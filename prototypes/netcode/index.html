Netcode Simulator

For each replication approach, what does each Client actually see compared with the Server's truth, how late is it, how much bandwidth does it use, and what breaks, under latency, jitter, loss, duplication, reordering and a bandwidth cap?

An authoritative Server runs the Match at 60 Ticks per second. Each Client shows what it has received. Below, the same Match runs through a simulated network; you pick how the Server and the Clients talk, then break the network and watch what each Client believes. Everything is seeded, so a scenario replays identically. Two approaches can run side by side on the same network conditions.

AEvent stream

The Server sends a message for everything that happens: an Enemy spawned, moved, fired or was destroyed, a Ship was destroyed, a Player moved or shot. The Client builds its picture of the Match from these messages alone.

  • Unreliable: each message is sent once. If it is lost, it is gone: an Enemy that never appears, or one that never dies.
  • Reliable and ordered: the Client confirms what it got, the Server resends the rest, and the Client applies messages strictly in order. One lost message holds back everything behind it until its resend arrives.

BSnapshots

Every Tick, each Client sends the keys its Player holds (one byte), repeating its last few inputs in every packet. Every K Ticks the Server sends each Client the position of every entity, unreliably. The Client keeps only the newest snapshot, so a lost one is simply replaced by the next. Spawns and deaths need no message: things appear in or vanish from the list.

CHybrid

B, plus a small reliable channel (confirmations and resends) for what a Player must not miss: a Player joined, left or timed out, an explosion, a Ship destroyed, game over. What is on screen never waits for this channel.

DTCP-like

The same snapshots as B, but on one reliable, ordered stream on the same lossy link, which is what TCP gives you. A lost packet is resent after a timeout, and everything sent after it waits until it arrives: head-of-line blocking.

ELockstep

Only inputs travel. Every Client runs the whole Match itself and moves to Tick t only once it has every Player's input for Tick t, relayed by the Server. Inputs are scheduled a few Ticks ahead (input delay) so they have time to arrive. One late input stops everyone.

      What the numbers mean

      Late by
      How far behind the Server's current Tick the newest Server state shown by this Client is. For A it is the newest Server Tick the Client has fully caught up with, so in quiet moments, when nothing moves and only heartbeats arrive, it can reach 250 ms plus latency.
      Position error
      Average distance between each entity this Client shows and the same entity on the Server right now. Fast Projectiles dominate it, and it grows with lateness even when nothing is wrong.
      Missing: wrong · late
      Entities the Server has that this Client does not show. Wrong: the entity already existed at the Tick the Client is showing, so it should be there. Late: it appeared after that Tick and is still on its way.
      Ghosts: wrong · late
      Entities this Client shows that the Server has removed. Wrong: removed before the Tick the Client is showing. Late: the removal is still on its way. Counted only while on screen.
      Own Ship reacts
      Time from a key change on this Client to the first screen of that Client showing the Server state that used it, averaged over the last 6 key changes.
      Down, Up, queue
      Bytes sent per second over the last second, headers included, for Server → Client and Client → Server. Queue: how long a packet sent now waits before it can leave, when a bandwidth cap is set.
      Packets to it
      Packets the Server sent to this Client, how many the network lost or duplicated, and how many messages or segments the Server resent.
      Held back, Waited
      Held back (A reliable, D): time during which packets had arrived but could not be used because an earlier one was missing. Waited (E): time this Client could not move to the next Tick.
      Crash noticed, behind real time
      Time from a Client crash until this Client learns that Player left. Behind real time (E): how far the whole Match has fallen behind the clock because everyone waited.

      Byte layout (assumed, not a spec)

      Network model

      • Each Client has two links, Server → Client and Client → Server, each with the same settings. 1 KB = 1000 bytes.
      • Latency is one way. Jitter adds a random 0 to jitter ms per packet but never reorders packets. Reordering is its own setting: that share of packets is held back 20 to 60 ms, so later ones overtake it.
      • Loss and duplication are independent per packet (no bursts). A duplicate arrives just after the original.
      • Bandwidth cap: a packet occupies the link for size ÷ cap. Packets wait in one first-in, first-out queue that never drops, so sending more than the cap turns into ever-growing delay.
      • Byte counts include the IPv4 and UDP (or TCP) headers.
      • Randomness depends only on the seed, the link, the Tick and the packet's position within that Tick, so both sides of a comparison see the same network luck.
      • The Server reads arriving packets once per Tick and each Client once per Frame, both every 16.7 ms here.

      Protocol details

      • Acknowledgements: every packet header carries the latest sequence number received and 32 bits for the 32 before it.
      • A, reliable and C: a message is resent when it has not been confirmed after the measured round trip + 50 ms.
      • D, TCP-like: a lost segment is resent after max(200 ms, 2 × measured round trip). No fast retransmit, no congestion control, no backoff.
      • A: Clients send an input message only when their keys change, plus a heartbeat after 250 ms of silence. Reliable A Clients also send a packet every Frame in which they received something, to acknowledge it. Unreliable A applies messages in arrival order and ignores messages about entities it does not know.
      • A: Projectiles are moved by the Client itself after the "fired" message; Enemies and Ships move only when a "moved" message arrives.
      • E: each packet repeats every input (or input bundle) not yet confirmed, up to 32 Ticks. Nobody runs more than one Tick per 16.7 ms, so time lost to waiting is never caught up.
      • A Player whose Client sends nothing for the timeout is removed and announced to the others.

      Game model and known simplifications

      • 640 × 360 playfield, no Star-field drawn. A Wave of Enemies spawns on the right every 4 s (first at 1.5 s) and drifts left. Enemies fire toward the Ship closest in height; Ships fire right. A destroyed Ship comes back after 2 s. The Match never ends, so there is no game over.
      • Players other than you follow a seeded script that changes their keys every 0.5 s.
      • Clients show the latest data they have. No interpolation, extrapolation or prediction: real Clients would smooth (adding delay) or predict their own Ship (hiding delay).
      • Sizes are uncompressed: no delta snapshots, no bit packing beyond the layout shown.
      • "Position error" compares each entity the Client shows with where the Server has it now, so it grows with lateness even when nothing is wrong.
