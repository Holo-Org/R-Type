R-Type language POCs

The same slice of R-Type, built four times: in C++, Rust, Zig and Odin. Each POC has its own report. This page lines their measurements up, for the team and for the comparative study the evaluator must validate before any development in a language other than C++. Choosing the language is left to the team.

Every figure comes from the four reports, and every judgement marked Assessment is a report's own. Where a report quoted another POC's figure, the owner's report is the source used here.

The slice every POC built

The spec is in language-pocs.md, and the layout follows ADR 0001: a thin Engine with a headless part and a client part, the Game on top, and a Server that must not link raylib.

  • Engine, headless: a little-endian byte writer and checked reader, a UDP transport with a network thread and a bounded inbox of 256 datagrams, a fixed-step clock.
  • Engine, client: window, drawing, textures, input, sounds from PCM samples and screenshots, over raylib 6.0.
  • Game: seven messages with their encoder and decoder, and the Match rules: up to 4 Players, Ship movement within 1280×720, a Player silent for 3 s dropped.
  • Server and Client: a headless 60 Hz Tick loop; a Client with a three-layer Star-field, four Ships from the provided sprite sheet, scripted input and a generated "pew".
  • Fuzz test: 10,000 round trips, then random and mutated datagrams, run with 100000 42.

Every datagram is an 8-byte header (protocol id "RT", version, message type, sequence) and a body, all little-endian. In all four, an Accept for Player 2 with sequence 0x01020304 is 52 54 01 02 04 03 02 01 02.

What the edits were. C++: game/match.cpp, then the module interface game/protocol.cppm. Rust: a spawn position in game/src/rules.rs, then a derive on ShipState. Zig: a spawn position in game/match.zig, then methods and a constant on ShipState. Odin: the spawn x in game/match.odin, then a field on Ship_State.

Why the edit costs differ. C++ recompiles one unit, or every importer of a changed interface. Rust recompiles the edited crate and its dependents. Zig compiles each program as one unit, with incremental compilation still experimental in 0.16.0. Odin keeps no cache at all, so every build is a full build; an internal, undocumented -internal-cached flag cut an unchanged Client rebuild to 0.07 s.

Debug on Apple Silicon. Zig 0.16's fast Debug backend is x86-64 only, so Zig's Debug times here go through LLVM; a teammate on an x86-64 machine would see different figures, not measured.

Assessment, from the reports: the Zig and Odin checks are the most complete, since they catch case 8, and also the most code to maintain; Cargo with cargo-deny is the cheapest for the dependency rules; C++ modules keep raylib's types out of the Engine's interface for free.

Interoperability

Every POC played against the ones before it, in both directions: each Server with four Clients from each other language, and each language's Clients on the other Servers. No mismatch was found.

  • Server answers. To the same hand-made connect, all four Servers answer with the same 549 bytes (an accept, then 30 snapshots), identical under cmp, Tick numbers included.
  • Client openings. What each Client sends first is identical across the four; capture windows caught two or three connects.
  • Mixed Matches. One Match on the Zig Server mixed C++, Rust and Zig Clients; one on the Odin Server had a Client in each of the four languages.
  • Timeouts. A Client killed with kill -9 was dropped 3.03–3.08 s later in every pairing, and the others were told.

What hurt, what was pleasant

The main points of each report's two sections, shortened.

C++

Hurt

  • Getting import std at all on macOS.
  • Toolchain defects found one after another: a GCC crash on a defaulted friend comparison, LLVM 21's AddressSanitizer hanging on macOS 26, a nondeterministic race between two xmake rules.
  • Editor support that needs clangd to match the compiler exactly.
  • Safety by discipline in the decoder.

Pleasant

  • xrepo: one line per dependency, raylib built in 25–30 s from nothing, a lock file, working Windows cross-builds.
  • Modules as encapsulation: raylib and Asio appear in two implementation units only.
  • Modern C++ reads well: std::expected, std::span, std::variant, std::println.
Rust

Hurt

  • Gaps in the raylib crate's safe API: three workarounds.
  • bindgen needs libclang on every machine; one binding brings 39 crates.
  • A macOS deployment-target mismatch between rustc and the cc crate.

Pleasant

  • One command builds everything, with the compiler pinned in the repository.
  • Compile times: 0.5 s for our code, under half a second per edit.
  • The decoder's ?, enum messages with exhaustive match, and a borrow checker that caught a real lifetime bug.
Assessment for the team: the language is the part that has to be learned, not the build.
Zig

Hurt

  • 87 MB of downloads on a first build, up to 7 minutes on a slow connection.
  • Every edit rebuilds whole programs: 5.4 s in ReleaseSafe.
  • A young toolchain: a standard-library function that does not compile, a fuzzer broken in Debug, silent deprecations.
  • macOS binaries tied to the build machine's macOS version.

Pleasant

  • Windows from the Mac with one flag.
  • One tool: no CMake, no libclang, not even git.
  • A compile-time codec with no per-message encoder or decoder, and std.Io's cancellable network thread.
Assessment for the team: a small language; what has to be learned is 0.16's new I/O, and Zig still breaks between releases.
Odin

Hurt

  • No build cache: every build is a full 4.1–4.6 s build.
  • The boundary is ours to enforce: 247 lines of checker.
  • Windows: no cross-link, and Visual Studio for the native build.
  • Semantic surprises: a range's upper bound evaluated on every iteration, empty UDP datagrams never sent.

Pleasant

  • Nothing to download or build but our code.
  • #packed structs of u16le and u32le fields as the wire format, with bit_set, exhaustive switches and or_return.
  • A parser in the standard library, built-in tests, and small binaries.
Assessment for the team: a small language that reads like C with better types; the risks are Windows, the checker to maintain, monthly breaking releases, and vendor: moving only with the compiler.

Not verified in any POC

  • Building on Linux, and building natively on Windows.
  • Running any Windows .exe.
  • Playing over a real network: every run used localhost.
  • Playing with the keyboard, and hearing the sound: every run was scripted.
  • Per-datagram agreement between the decoders.
  • Behaviour after very long runs, when Tick and sequence counters wrap.
